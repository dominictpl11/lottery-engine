# Python版高并发抽奖系统需求文档

## 1. 项目定位

本项目用于将现有 Java 抽奖引擎重建为 Python 技术栈版本，目标不是简单 CRUD，而是实现一个可写入简历的高并发营销抽奖系统。系统应支持活动配置、奖品配置、概率抽奖、库存扣减、用户限流、抽奖记录落库、异步发奖和后续补偿。

第一阶段以可运行的 MVP 为目标，优先保证核心抽奖链路清晰、稳定、可测试；后续再补充异步发奖、规则引擎、压测和监控。

## 2. 技术栈

第一阶段：

- Python 3.10+
- FastAPI：HTTP API 服务
- SQLAlchemy：数据库 ORM
- SQLite：本地快速启动数据库
- Redis：库存缓存、限流、防重复抽奖
- Pydantic：请求与响应模型
- Uvicorn：本地开发服务

第二阶段：

- MySQL 或 PostgreSQL：替换 SQLite，作为正式业务库
- Alembic：数据库迁移
- Celery + RabbitMQ 或 Redis Stream：异步发奖
- APScheduler：活动状态扫描、失败补偿
- pytest：单元测试和接口测试
- Locust：抽奖接口压测
- Docker Compose：一键启动依赖环境

## 3. 核心业务目标

用户在活动有效期内参与抽奖，系统完成活动校验、用户频率校验、库存扣减、概率抽奖、订单记录、中奖结果返回。中奖后的奖品发放可以在第一阶段同步模拟，第二阶段改为异步任务。

核心链路：

1. 用户请求抽奖接口。
2. 系统校验活动是否存在、是否运行中、是否在有效期内。
3. 系统校验用户是否超过参与频率限制。
4. 系统校验并扣减活动库存。
5. 系统按活动配置的奖品概率执行抽奖。
6. 若中奖，扣减奖品库存。
7. 系统生成抽奖订单。
8. 系统返回抽奖结果。
9. 后续异步发奖服务处理奖品发放。

## 4. 第一阶段 MVP 功能

### 4.1 活动管理

支持创建活动，活动字段包括：

- 活动 ID
- 活动名称
- 活动描述
- 开始时间
- 结束时间
- 活动库存
- 每人每日参与次数
- 活动状态

活动状态：

- draft：草稿
- running：运行中
- closed：已关闭

第一阶段可以通过 API 创建活动，不实现复杂后台页面。

### 4.2 奖品配置

支持给活动配置多个奖品，奖品字段包括：

- 奖品 ID
- 活动 ID
- 奖品名称
- 奖品类型
- 奖品内容
- 奖品库存
- 剩余库存
- 中奖概率权重

奖品类型：

- text：文字类奖品，例如“谢谢参与”
- coupon：优惠券
- physical：实物奖品

### 4.3 抽奖接口

接口：

```http
POST /api/lottery/draw
```

请求示例：

```json
{
  "user_id": "user_001",
  "activity_id": 100001
}
```

响应示例：

```json
{
  "success": true,
  "order_id": "202606220001",
  "user_id": "user_001",
  "activity_id": 100001,
  "draw_state": "won",
  "award_id": 1,
  "award_name": "100元优惠券",
  "message": "中奖"
}
```

### 4.4 抽奖订单

每次成功进入抽奖流程都要生成订单，字段包括：

- 订单号
- 用户 ID
- 活动 ID
- 奖品 ID
- 抽奖状态
- 发奖状态
- 创建时间

抽奖状态：

- won：中奖
- missed：未中奖
- rejected：未通过校验

发奖状态：

- pending：待发放
- sent：已发放
- failed：发放失败
- none：无需发放

### 4.5 高并发控制

第一阶段必须实现：

- Redis 活动库存扣减，避免超卖。
- Redis ZSet 滑动窗口限流，限制用户短时间重复抽奖。
- 订单幂等控制，避免重复请求造成重复发奖。

本地没有 Redis 时，允许应用降级到进程内实现，方便开发启动；但文档和代码应保留 Redis 接口，方便后续替换。

## 5. 第二阶段增强功能

### 5.1 异步发奖

中奖后不直接发放奖品，而是写入发奖任务队列，由 Worker 异步处理。

候选方案：

- Celery + RabbitMQ
- Celery + Redis
- Redis Stream

要求：

- 发奖失败可重试。
- 多次失败后记录失败原因。
- 发奖结果回写订单表。

### 5.2 规则引擎

抽奖前增加规则链：

- 活动状态规则
- 活动时间规则
- 用户参与次数规则
- 活动库存规则
- 黑名单规则

Python 实现可以使用责任链模式，便于后续迁移到 Java。

### 5.3 压测和性能优化

使用 Locust 对抽奖接口压测，重点观察：

- QPS
- 平均响应时间
- P95/P99 响应时间
- 库存是否超卖
- 订单是否重复

## 6. 非功能需求

- 接口响应应统一结构，便于前后端或测试脚本使用。
- 核心业务逻辑应分层，避免全部写在 Controller 中。
- 数据库操作应通过 Repository 封装。
- 抽奖算法应独立于接口层，便于测试。
- Redis 相关能力应封装为基础设施服务。
- 关键流程应输出日志。
- 第一阶段应支持本地一条命令启动。

## 8. 第一阶段验收标准

完成以下能力即可视为 MVP 通过：

1. 可以启动 FastAPI 服务。
2. 可以访问健康检查接口。
3. 可以创建活动。
4. 可以配置奖品。
5. 可以执行抽奖。
6. 抽奖订单可以落库。
7. 活动库存不会扣成负数。
8. 奖品库存不会扣成负数。
9. 同一用户短时间高频请求会被限制。
10. Swagger 文档可访问。

## 9. 简历表述方向

项目名称：

高并发营销抽奖系统

技术栈：

Python、FastAPI、SQLAlchemy、Redis、Redis Lua、Celery、RabbitMQ、Docker、pytest、Locust

简历亮点：

- 基于 FastAPI 构建营销抽奖系统，支持活动配置、奖品配置、概率抽奖、订单落库和发奖状态追踪。
- 使用 Redis + Lua 实现库存原子扣减，解决高并发抽奖超卖问题。
- 使用 Redis ZSet 实现滑动窗口限流，限制用户短时间重复参与活动。
- 设计抽奖订单幂等机制，避免重复请求导致重复扣库存和重复发奖。
- 使用 Celery + RabbitMQ 实现中奖后异步发奖，解耦抽奖链路和发奖链路。
- 使用 Locust 对抽奖接口进行压测，并基于压测结果优化库存扣减流程。
